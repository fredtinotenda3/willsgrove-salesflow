# Willsgrove SalesFlow — Master Roadmap

Single cross-milestone source of truth for what exists, what's in flight, and what's deliberately deferred. Update this file in the same round as every milestone/stage delivery — before packaging the zip — so a later milestone never duplicates or quietly conflicts with something already built.

This file is a map, not a spec. For the authoritative detail on any completed milestone, see its section in `PROGRESS.md`. For the authoritative detail on the in-flight one, see the design note linked from its row below until it's folded into `PROGRESS.md` on completion.

## Status legend

- ✅ **Done** — implemented, tested, delivered.
- 🚧 **In progress** — design agreed and/or partially built.
- 📝 **Proposed** — written up, awaiting confirmation before build starts.
- ⏳ **Deferred** — intentionally not built yet; a placeholder (nav link, schema comment, enum gap) may already exist pointing at it.

## Things to never conflate

- **Warehouse picking (Milestone 3)** vs. **SAP-catalogue/price verification & discount approval** (`VerificationStatus`/`PriceDecisionStatus`/`OrderApproval`, deferred, unused) — different departments, different gates, different models. See the table row above.
- **`StockSnapshot`/`StockSnapshotLine`** (Milestone 1, point-in-time SAP on-hand inventory import, for future stock-availability checks at order-entry time) vs. a picking session's per-order found/unavailable record (Milestone 3, order-specific, not a snapshot of SAP stock).
- **Warehouse unavailability vs. customer decision vs. actual lost sale (Milestone 4's own central rule)** — `UnfulfilledDemand.unavailableQuantity` is what the warehouse couldn't supply; a `CustomerDecisionEvent` is what the customer decided to do about it; `LostSaleRecord`/`confirmedLostQuantity` is a genuine lost sale, and is **never** implied automatically by either of the other two. A cancelled quantity is not the same as a confirmed-lost quantity — see PROGRESS.md's Milestone 4 section.
- **Authorized quantity vs. invoiced quantity vs. remaining quantity (Milestone 5)** — `PickingLine.foundQuantity` on an `AUTHORIZED` session is what the warehouse actually picked; `SapInvoiceLine.quantityInvoiced` (summed, live, excluding cancelled/reversed invoices) is what SAP actually billed; the remaining quantity is their signed difference, **never clamped to zero** on over-invoicing. None of the three is ever stored as a column on `OrderLine` itself — all are computed live. See PROGRESS.md's Milestone 5 section.
- **Invoice-header reconciliation status vs. order-line invoice status (Milestone 5's own central rule)** — `SapInvoice.reconciliationStatus` (`UNMATCHED`/`PARTIALLY_MATCHED`/`RECONCILIATION_REQUIRED`/`MATCHED`/`CANCELLED_REVERSED`) describes one SAP invoice and its lines; `OrderLineInvoiceStatusValue` (`NOT_YET_INVOICED`/`PARTIALLY_INVOICED`/`FULLY_INVOICED`/`OVER_INVOICED`) describes one order line against every invoice ever matched to it. They are computed by entirely different functions over entirely different value sets and must never be read as interchangeable.
- **A warehouse lost sale (Milestone 4) vs. an actual SAP invoice shortfall (Milestone 5)** — both can ultimately trace back to the same `PickingLine`, but a confirmed lost sale is a customer-decision fact recorded in `LostSaleRecord`, while an invoice reconciliation exception is a billing-accuracy fact recorded against `SapInvoiceLine`. Neither module reads or infers from the other's tables.
- **Customer complaint vs. rejection vs. quantity dispute vs. physical return vs. SAP credit note vs. confirmed financial loss (Milestone 6A's own central rule)** — an `InvoiceClaim` records the first three and a *recommended* resolution for the rest; it never creates an accounting transaction, never alters SAP invoice data, and never marks a credit note as issued merely because someone recommended one. `ClaimResolution.approvedCreditAmount` is an *approved exposure* figure, not proof SAP has credited anything — `computeClaimFinancialSummary()`'s `actualSapCreditedAmount` is always `null`/`actualCreditDataAvailable: false` in 6A, by design, because that fact can only come from a real SAP credit note (Milestone 6B).
- **A claim's "already claimed elsewhere" quantity (Milestone 6A) vs. Milestone 5's invoiced quantity** — `getAlreadyClaimedQuantity()`/`getAlreadyClaimedTotal()` sum `InvoiceClaimLine.acceptedQuantity + rejectedQuantity` across every claim against one `SapInvoiceLine`, always live, never stored; this is a disputes-filed total, structurally separate from Milestone 5's `getInvoicedQuantity()` (a billed-amount total). Neither function reads the other's result.
- **A `ClaimResolution`'s approved amount (Milestone 6A) vs. a `CreditNote`'s actual amount (Milestone 6B)** — `ClaimResolution.approvedCreditAmount` is what an internal manager approved; `CreditNote.amount` is what SAP actually issued, entered by a human or imported from a real SAP export, never derived or estimated from the claim's lines. `computeClaimFinancialSummary()`'s `actualSapCreditedAmount` sums only real `CreditNote` rows; `actualExceedsApproved` flags (never clamps) the case where the two diverge in SAP's favor. SalesFlow never creates a `CreditNote` document in SAP — every 6B write only records that SAP already did.
- **Claim-status auto-advance (Milestone 6B) is a ratchet, not a toggle** — `recomputeClaimStatusAfterActuals()` only ever moves a claim's status forward (`APPROVED`→`PARTIALLY_RESOLVED`→`RESOLVED`) along edges `CLAIM_STATUS_TRANSITIONS` (6A) already allows, and re-validates against that graph immediately before every write rather than trusting its own pure decision function blindly. It never reverses an already-applied auto-advance when a `CreditNote`/`ClaimReturn` is later unlinked, reopened, or marked cannot-link — that correction is a deliberate manual action (6A's own status-change route), not an automatic side effect of fixing an unrelated record's match.
- **A quotation vs. the order it may eventually become (Milestone 7's own central rule)** — a `Quotation` is never a `CustomerOrder` in a pre-order status, and `ACCEPTED` never auto-creates an order: `convertQuotationToOrder()` is always a separate, explicit, idempotent action the quotation's own detail page triggers, guarded twice against ever producing a second order for the same quotation. A quotation revision is a brand-new `Quotation` row (`previousRevisionId`/`rootQuotationId`), never an edit of an already-issued one, and a superseded row keeps its own frozen status forever rather than becoming a `SUPERSEDED` value — default list/dashboard queries exclude it by `supersededAt`, not by status. Don't read `Quotation.total`/line amounts as live-computed — like `CustomerOrder`'s own totals, they are stored at write time and only ever recomputed while the quotation is still DRAFT.
- **Milestone 8's `ApprovalPolicy`/`ApprovalRequest` framework vs. the legacy, unused M0 `ProductVerification`/`PriceDecision`/`OrderApproval` schema** — the M0 models are dead and order-line-scoped; they were never wired up by any milestone and Milestone 8 does not use, migrate, or build on them. Milestone 8's models are the live, cross-module framework. See the "Pricing/discount verification & approval" row above.
- **Configurable vs. enforced (Milestone 8's own central rule)** — an `ApprovalPolicy` existing, active, and correctly configured for `ApprovalModule.ORDERS` does **not** mean order creation is actually gated by it. `ApprovalActionType.ORDER_VALUE_EXCEEDS_THRESHOLD` is framework-ready only, by explicit instruction: the policy UI visibly labels it "Not yet enforced," and `lib/orders.ts`'s `createOrderCore` has no call into the approval framework at all. Only `QUOTATION_DISCOUNT_EXCEEDS_THRESHOLD` is actually live, via `checkAndRequireQuotationApproval` in `issueQuotation`. Don't assume a policy row being creatable means the workflow it describes is enforced — check `lib/approvals/policy-queries.ts`'s `ENFORCED_ACTION_TYPES` set.
- **Mock-tested vs. real-SAP-tested (Milestone 9's own central rule)** — every SAP sync/submission path in this milestone has been exercised against the deterministic `MockSapAdapter` only. `ServiceLayerAdapter` is written against SAP's standard Service Layer object model but has never been run against a real SAP Business One tenant, because no real credentials/endpoint/company database were ever available or guessed. Don't read "implemented" as "verified against real SAP" anywhere in this milestone — see `docs/sap-integration/discovery-checklist.md` for exactly what must be confirmed first, and PROGRESS.md's Milestone 9 section for the honest verification results.
- **SAP submission eligibility (Milestone 9) vs. Milestone 8's Orders approval gate vs. the legacy M0 price-verification schema** — three separate things. `checkOrderEligibility` (M9) requires `CustomerOrder.source === "QUOTATION"` with no live approval blocking the source quotation, because that is the only path with a genuine Sales-approved price (`OrderLine.customerUnitPrice`). It does **not** call into, and does not depend on, `ApprovalActionType.ORDER_VALUE_EXCEEDS_THRESHOLD` (M8, still framework-ready only) or the legacy M0 `VerificationStatus`/`PriceDecisionStatus`/`OrderApproval` schema (dead, unused). A manually-entered order can never become SAP-submission-eligible today, regardless of its approval state, until a future milestone builds the missing pricing/approval workflow those other two rows gesture at.
- **A `MessageIntake` (Milestone 10) vs. a real PO intake/order (Milestone 2A/2B)** — a `MessageIntake` row is created the instant an email/WhatsApp message or a manually-logged one arrives, by the webhook/manual-intake route itself, with no signed-in reviewer involved at all (`reviewedById` stays `null` until a human acts). It never becomes a commercial transaction on its own: converting it calls the EXISTING, unmodified `createPoIntake()` (M2A/M2B) and attributes the resulting `OrderDocument` to the REVIEWER who made that call, never to the message or any synthetic "system" actor. Don't read a `RECEIVED` `MessageIntake` as a pending order — it is pre-review inbox content, structurally incapable of creating anything by itself.
- **`OutboundMessage` (Milestone 10) vs. `Notification` (Milestone 8)** — a `Notification` is in-app, for a SalesFlow user (Milestone 8's polled bell); an `OutboundMessage` is customer-facing, sent out over email/WhatsApp (or recorded as sent by the mock adapter). They are two separate, unrelated models with no shared table or cross-reference — recording one never implies or creates the other.
- **`DispatchRecord.status`/`DeliveryOutcome` (Milestone 10) vs. `OrderStatus` (Milestone 0/3)** — same "own lifecycle, never touch the shared enum" discipline every prior milestone that added a parallel state machine (`PickingSessionStatus`, M9's `IntegrationOperationStatus`) already followed. `OrderStatus` stops at `READY_TO_INVOICE`; dispatch/delivery facts live entirely on `DispatchRecord`/`DeliveryRecord`, with `getOrderFulfilmentStatus()` deriving a live summary rather than either model writing back a second "true" status onto `CustomerOrder`.
- **A `DeliveryLine` rejection (Milestone 10) vs. an `InvoiceClaim` (Milestone 6A)** — recording a rejected/shortage quantity on delivery never auto-creates an `InvoiceClaim`. The delivery UI only ever offers a link into the EXISTING `/invoice-claims/new` flow for a human to file one explicitly — `InvoiceClaim.customerOrderId` is "where possible," and a SAP invoice (the claim's real anchor) usually doesn't exist yet at delivery time anyway.
- **`CustomerOrder.salespersonId` (Milestone 11) vs. `CustomerOrder.createdById`** — `createdById` is whoever actually created the row in SalesFlow (could be any role, including a manager entering on someone's behalf); `salespersonId` is the assigned salesperson for reporting/filtering purposes. **Corrected by Milestone 12**: the sentence that used to end this bullet ("defaulting to `createdById` only when no better value is known") described a real data-integrity gap, not a feature — it is no longer true of any order created after Milestone 12 shipped (`createOrderCore` now leaves `salespersonId` genuinely `NULL` rather than silently defaulting it), and was never something to rely on even for pre-M12 rows, since it couldn't be distinguished from a deliberate pick. Still carried through from `Quotation.salespersonId` on conversion. Never read `salespersonId`'s mere presence as proof of a deliberate choice — check `lib/reporting/attribution.ts`'s confidence tier instead.
- **A reporting figure's data-quality label (Milestone 11) is about the FIGURE, not the report** — `actual`/`calculated`/`provisional`/`missing` is set per metric (`QualifiedMetric<T>`, `lib/reporting/types.ts`), never a single blanket label for an entire report response. A report can — and several do — mix actual counts with a `missing` figure in the same payload (e.g. communications monitoring's `deliveryReceiptsSupported: false`) without that making the rest of the report provisional.
- **A status-equality filter applying to a report (Milestone 11) is never assumed from the field merely being accepted** — `ReportFilters` carries all 5 status dimensions on every request so the shared filter bar has somewhere to put them, but a given report function only actually uses the ONE dimension (if any) its own top comment says it does; see `docs/milestones/m11-metric-definitions.md` section 6 before assuming a filter field does anything in a report you haven't checked.
- **`CurrencyExposureBucket.actualSapCreditedAmount` (Milestone 6B, claim-centric) vs. Milestone 13's own `CustomerCommercialHealth.actualCreditNotes` (customer-centric)** — both are real, live sums of `CreditNote` rows, but over different populations: 6B's figure runs per-claim, across every claim against a given SAP invoice; Milestone 13's figure runs per-customer, across a union of claim-linked **and** direct-invoice-linked (`claimId: null`) credit notes, counted once each with no double-counting across the two branches. They are shown side by side on the Customer 360 profile with distinguishing labels and are never added together or treated as reconciling exactly against one another.
- **A Customer 360 profile fact (Milestone 13) vs. the management customer-intelligence overview's own ranking (Milestone 13)** — the profile (`/customers/[id]`, all 3 roles) shows one customer's own figures in full, with no ranking context; the overview (`/reports/customer-intelligence`, management-only) ranks every eligible customer against each other, per dimension, per currency where money is involved, with **no composite score and no tier**. Neither page derives from the other at request time (though both ultimately read `lib/reporting/customer-revenue-queries.ts`'s `getCustomerIntelligenceOverview`/`getCustomerRevenueProfile`, which share the same qualifying-invoice rules by construction) — a customer absent from a currency's revenue ranking simply has no activity in that currency, never ranked against zero.
- **A Product 360 profile fact (Milestone 14) vs. the management product-intelligence overview's own ranking (Milestone 14)** — same pairing discipline as Milestone 13's customer pages, one level down: the profile (`/products/[id]`, all 3 roles) shows one product's own figures in full, with no ranking context; the overview (`/reports/product-intelligence`, management-only) ranks every product against every other across exactly 10 independent dimensions, **never combined into one composite score and never bucketed into an invented tier**. A product's `Product.id` only exists as a route key when a real master record exists — an unmatched SAP item code has no profile page at all, and surfaces only through the overview's 10th ("incomplete/unmatched master data") dimension, which carries no `rank` field since it is a binary flag, not a ranked magnitude.
- **A claim/return/credit-note's inclusive count (Milestone 14) vs. its conservative, attribution-gated value (Milestone 14)** — `getProductClaimAndReturnOverview`'s `claimCount`/`returnCount` include every claim or return that touches a product's SAP item code at all, even one raised on a multi-product invoice; `getProductCreditNoteValueOverview`'s per-product currency totals and `getProductClaimAndReturnOverview`'s `multiProductClaimCount` are the opposite discipline — a credit note or claim is only ever attributed to one product's financial figures when `resolveSingleProductSapItemCode` finds every line on it resolves to that same single SAP item code; a multi-product record is excluded from every product's financial total and counted instead in its own explicit `multiProductClaimCount`/`unattributableCreditNoteCount` bucket, never guessed or split pro-rata. Do not read the inclusive count and the attribution-gated value as reconciling against one another — they are deliberately different populations.
